0 這個專案做什麼

先建立直覺，再看代碼。

掛單簿（Order Book）是加密貨幣交易所的核心 UI。 它即時顯示市場上所有未成交的買單（Bid）和賣單（Ask），讓交易者看清楚「現在哪個價格有多少人想買、哪個價格有多少人想賣」。

紅色 = 賣單（Ask），綠色 = 買單（Bid），中間 = 最後成交價。

這個專案的目標：

  • 連接 BTSE 交易所的 WebSocket，接收 BTC 永續合約的即時掛單資料
  • 每邊顯示 8 筆（離目前成交價最近的 8 個報價）
  • 顯示每個報價的累計量（Total），以及對應的深度百分比 bar
  • 報價有異動時顯示閃爍動畫（新報價閃整列、size 增減閃該格）
  • 中間顯示最後成交價，漲顯示綠色，跌顯示紅色

3 核心型別

讀懂型別定義，後面的程式碼都在操作這些東西。

src/types.ts// WS 原始資料：價格和數量都是「字串」（交易所 API 的設計慣例）
export type PriceLevel = [price: string, size: string]

// 帳本狀態：key = 價格（數字），value = 數量（數字）
export type Book = Map<number, number>

// WS 收到的一包資料（可能是 snapshot 也可能是 delta）
export interface OrderBookData {
  bids: PriceLevel[]     // 買單列表
  asks: PriceLevel[]     // 賣單列表
  seqNum: number         // 這包的序號
  prevSeqNum: number     // 上一包的序號（用來偵測掉包）
  type: 'snapshot' | 'delta'
  symbol: string         // 交易對，例如 'BTCPFC'
  timestamp: number
}

// 一列報價準備好要渲染的資料
export interface DisplayRow {
  price: number           // 報價
  size: number            // 數量
  total: number           // 累計數量（從 spread 往外累加）
  percent: number         // 0~1，total / 這邊最大的 total（深度 bar 用）
}

export type PriceTrend = 'up' | 'down' | 'same'
export type ConnStatus = 'connecting' | 'open' | 'closed'

PriceLevel → Book 的轉換：WebSocket 給的是字串 tuple， 程式碼裡先 Number(priceStr) 轉成數字，存進 Map<number, number>。 這個轉換在 applyLevels() 裡發生一次，之後整個程式都用數字操作。

4 WebSocket：snapshot + delta

BTSE 的設計思路：不是每次都傳整本帳，只傳改動的部分。

  • 第一包：snapshot — 完整帳本現況，所有 price level 全部在裡面
  • 之後每包：delta — 只傳「有改動的部分」：有新報價就加，有人取消就把 size 設為 0

連線後先送 subscribe，server 自動推 snapshot：

hooks/useOrderBook.tsws.send(JSON.stringify({ op: 'subscribe', args: ['update:BTCPFC'] }))

處理收到的資料：

hooks/useOrderBook.ts — onmessageif (data.type === 'snapshot') {
  resyncPending.current = false          // 新 snapshot 到了，解除 resync guard
  const built = applySnapshot(data)       // 建新的 bids / asks Map
  asksBook.current = built.asks
  bidsBook.current = built.bids
  lastSeq.current = data.seqNum
  flush()
}
if (data.type === 'delta') {
  if (!isContinuous(data.prevSeqNum, lastSeq.current)) {
    resync()                               // 掉包了，重新訂閱
    return
  }
  applyLevels(asksBook.current, data.asks) // 把改動合併進去
  applyLevels(bidsBook.current, data.bids)
  lastSeq.current = data.seqNum
  if (isCrossed(bidsBook.current, asksBook.current)) {
    resync()                               // 帳本矛盾，也要重新訂閱
    return
  }
  flush()
}

5 帳本狀態：Map 為什麼比 Array 好

資料結構的選擇直接影響代碼複雜度。

帳本的本質是「每個價格對應一個數量」，這正是 Map<price, size> 的用途：

lib/orderBook.ts — applyLevelsexport function applyLevels(book: Book, levels: PriceLevel[]): void {
  for (const [priceStr, sizeStr] of levels) {
    const price = Number(priceStr)
    const size  = Number(sizeStr)
    if (size === 0) book.delete(price)    // size=0 = 這個報價被撤銷
    else           book.set(price, size)   // 新增或更新
  }
}

如果用 Array：每次收到 delta，你得先 findIndex 找那個 price 的位置，再 splice 或 filter——O(n) 查找。 Map 的 set / delete / has 都是 O(1)。

Book 放 useRef 而不是 useState：Map 是可變結構，每次 delta 都直接 mutate 它（book.set/delete）。 React 的重新渲染不是每次 Map 改動就觸發，而是由 flush() 裡的 setAsks/setBids 控制—— 這讓高頻 delta 不會造成過多的重新渲染。

6 seqNum 缺口偵測與 re-subscribe

網路不可靠；掉包時帳本狀態必須恢復，這是這個作業最核心的考點。

為什麼需要 seqNum 檢查

每一包 delta 都有 prevSeqNum 欄位，表示「我是接在 seqNum=X 那包之後的」。 如果 delta.prevSeqNum ≠ 我上次處理的 seqNum，代表中間有包掉了， 本地帳本已經和交易所不同步。這時候不能繼續 apply delta，必須重新訂閱拿新 snapshot。 

lib/orderBook.ts — isContinuous（純函式，可單元測試）export function isContinuous(prevSeqNum: number, lastSeqNum: number | null): boolean {
  if (lastSeqNum == null) return false   // 還沒收過 snapshot，不連續
  return prevSeqNum === lastSeqNum
}

resync：重新拿 snapshot

hooks/useOrderBook.ts — resync()const resync = () => {
  if (resyncPending.current) return    // guard：在新 snapshot 到之前不重複觸發
  resyncPending.current = true
  lastSeq.current = null
  unsubscribe(ws)
  subscribe(ws)    // server 收到後重推完整 snapshot
}
為什麼需要 resyncPending guard： resync() 把 lastSeq = null，導致接下來每包 delta 的 isContinuous 都回傳 false， 每包都再呼叫一次 resync()——連鎖 unsubscribe + subscribe。 guard 確保：在新 snapshot 到達（把 resyncPending 重置為 false）之前，所有 delta 都直接跳過。

Crossed orderbook 偵測

「Crossed」代表最佳買單價格 ≥ 最佳賣單價格——邏輯上不可能，表示帳本狀態錯誤。 每次 apply delta 後都呼叫 isCrossed，一旦成立就視同掉包呼叫 resync()。 

lib/orderBook.ts — isCrossedexport function isCrossed(bids: Book, asks: Book): boolean {
  if (bids.size === 0 || asks.size === 0) return false   // 空帳本不算 crossed
  const bestBid = Math.max(...bids.keys())
  const bestAsk = Math.min(...asks.keys())
  return bestBid >= bestAsk
}

7 累計 total 與深度百分比

規格書規定的累計方向，跟你直覺想的可能不同。

「Total」不是某個報價的 size，而是「從 spread 到那個報價，中間所有報價的 size 加起來」。 規格書規定：

  • 賣單（Sell）：從最低價（best ask，最靠近 spread）開始往上累加
  • 買單（Buy）：從最高價（best bid，最靠近 spread）開始往下累加
lib/orderBook.ts — selectRows（核心演算法）export function selectRows(book: Book, side: Side, rows: number = ROWS): DisplayRow[] {
  const entries = [...book.entries()]
  const sorted =
    side === 'sell'
      ? entries.sort((a, b) => a[0] - b[0])  // 升序：最低價在前（best ask 先累加）
      : entries.sort((a, b) => b[0] - a[0])  // 降序：最高價在前（best bid 先累加）
  const top = sorted.slice(0, rows)           // 取最靠近 spread 的 8 筆

  let cumulative = 0
  const withTotals = top.map(([price, size]) => {
    cumulative += size
    return { price, size, total: cumulative }
  })
  const maxTotal = cumulative || 1            // 最後一筆 cumulative = 這邊的最大值
  const display = withTotals.map((r) => ({
    ...r,
    percent: r.total / maxTotal,              // 0~1，深度 bar 的寬度用這個
  }))

  // 賣單：累加後最低價（best ask）total 最小；顯示時它要在底部（靠近 last price）
  // 所以反轉：最高價（total 最大）在頂端
  return side === 'sell' ? display.reverse() : display
}
最容易搞混的地方：賣單先升序排（讓 best ask 先被累加），但顯示時要反轉（讓 best ask 在底部、靠近 last price）。 買單直接降序排（best bid 在頂），累加後不需要反轉。

8 requestAnimationFrame 批次更新

高頻 WebSocket 訊息與 React 重新渲染的協調。

BTSE 的 delta 大約每 200–500ms 一批，偶爾短時間連發多包。 如果每收到一包就 setState，React 可能每秒重渲染幾十次—— 大部分 render 對人眼來說是無意義的，只是在浪費 CPU。 

hooks/useOrderBook.ts — flush()const flushQueued = useRef(false)
const lastFlushAt  = useRef(0)

const doFlush = () => {
  flushQueued.current = false
  lastFlushAt.current = Date.now()
  setAsks(selectRows(asksBook.current, 'sell'))  // 觸發 React re-render
  setBids(selectRows(bidsBook.current, 'buy'))
}

const flush = () => {
  if (flushQueued.current) return   // 已排隊等下一幀，跳過這包
  flushQueued.current = true
  const elapsed = Date.now() - lastFlushAt.current
  const wait = Math.max(0, throttleMsRef.current - elapsed)
  if (wait === 0) {
    requestAnimationFrame(doFlush)           // 下一幀才真正 setState
  } else {
    setTimeout(() => requestAnimationFrame(doFlush), wait)  // 節流模式加延遲
  }
}
rAF 的好處： requestAnimationFrame 自動與螢幕的 vsync 對齊（通常 60fps，即每 16ms 一幀）。 無論 WebSocket 多快丟資料，React 最多每幀更新一次畫面。 按下節流按鈕後，throttleMsRef.current = 300，flush 至少間隔 300ms 才觸發， 方便肉眼觀察帳本變化。

9 閃爍動畫：useFlash + Web Animations API

hooks/useFlash.tsexport function useFlash(
  ref: RefObject<HTMLElement | null>,
  token: number | null,   // null = 不閃；傳入非 null 的新 token = 觸發閃爍
  color: string,
): void {
  const lastToken = useRef<number | null>(null)
  useEffect(() => {
    if (token == null || token === lastToken.current) return
    lastToken.current = token
    const el = ref.current
    if (!el) return
    el.animate(
      [{ backgroundColor: color }, { backgroundColor: 'transparent' }],
      { duration: 400, easing: 'ease-out' },
    )
  }, [token, color, ref])
}

使用 Web Animations API（element.animate()）而不是 CSS class toggle 的原因：

  • 快速連續觸發時，瀏覽器自動「取消舊動畫、重新播放新動畫」，不需要手動清理
  • 動畫跑在 compositor thread，不阻塞主線程
  • 顏色可以動態傳入（紅或綠由外部決定），不需要定義 CSS keyframe
如果改用 CSS class toggle 的問題： 必須先 remove class → 等一幀 reflow → 再 add class，才能讓動畫重新播放。 在高頻更新下容易遺漏閃爍。element.animate() 每次呼叫都建立新的 Animation 實例，瀏覽器原生處理堆疊。

10 OrderBookSide：每幀 diff 出誰要閃

只有「有變動的列」才閃，沒變的不要觸發動畫。

OrderBookSide 保留上一幀的 Map<price, size>，每次重新渲染時和新資料比較：

components/OrderBookSide.tsxconst prevSizes = useRef<Map<number, number>>(new Map())
const tokenRef  = useRef(0)
tokenRef.current += 1           // 每次 render 遞增，代表「這是一個新的 tick」

const hydrated = prevSizes.current.size > 0   // 第一次不閃（避免初始 snapshot 全部 8 列同時閃）

const annotated = rows.map((r) => {
  const prev    = prevSizes.current.get(r.price)
  const isNew   = hydrated && prev === undefined          // 上幀沒有這個 price → 新報價
  const sizeDir = prev === undefined ? null
                : r.size > prev ? 'up'
                : r.size < prev ? 'down' : null          // size 增 or 減
  return { ...r, isNew, sizeDir }
})

// 在子元件的 effect 之後才更新 prevSizes（讓子元件先拿到正確的 diff）
useEffect(() => {
  const next = new Map<number, number>()
  for (const r of rows) next.set(r.price, r.size)
  prevSizes.current = next
})
為什麼 prevSizes 在 effect 裡更新： React 保證父元件的 effect 在子元件的 effect 之後才執行。 所以 OrderBookRow 裡的 useFlash effect 先比較 token 並觸發動畫， 之後 OrderBookSide 的 effect 才把 prevSizes 更新成新值。 如果在 render 期間直接更新 prevSizes，子元件就看不到差異，閃爍邏輯失效。

12 離線 Mock Feed

設計讓 hooks 不需要知道它連的是真實還是假的 WebSocket。

lib/socket.ts — 唯一切換點export const USE_MOCK = import.meta.env.VITE_MOCK === '1'

export function createSocket(url: string): WebSocket {
  if (USE_MOCK) return new MockSocket(url) as unknown as WebSocket
  return new WebSocket(url)
}

MockSocket（lib/mockFeed.ts）實作和真實 WebSocket 相同的介面，行為：

  • 初始：推送一次完整 50-level snapshot
  • 每 450ms：推一批 delta（隨機改 1–3 個 price level）
  • 每 800ms：推一筆 trade（更新 last price）
  • 偶爾 size=0（刪除一個 level）→ 觸發新報價出現的閃爍
設計原則：useOrderBook 和 useLastPrice 只呼叫 createSocket(url)， 不知道底下是真的還是假的。這讓 demo、截圖、CI 完全不需要外部連線， 也讓你在本機隨時能看到動畫效果。
